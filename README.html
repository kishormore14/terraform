kaito-nexus-onprem-infra

Terraform scripts that build a complete Nexus environment inside a client's own cloud account: network, database, document storage, secrets, entry point, software, and identity service.

⚠️
Important Location Notice:
Documents live in kaito-mywork/docs/changes/, not in this repository. Start with the High Level Design, then the AWS Low Level Design. dev-account-setup.md explains how to create and prepare the development AWS account.

Amazon Only

aws/ is the only cloud folder, and it is the only one being built. There is no azure/ or gcp/ folder, because an empty folder claims something exists that does not. If a second cloud is ever needed, it becomes a sibling of aws/ and the expensive part is the resources inside it, not the move.

What is Where

Folder What it is Lifetime
aws/bootstrap/ Creates the bucket that holds Terraform's records. Run once, before anything else, because Terraform cannot create the place it keeps its own record. Once
aws/network/ The private network, the three web addresses and the certificate. Long-lived, rarely changed
aws/data/ The database and the document store — the two things that hold information and could not be recreated if lost. The second step of removal. Long-lived, must survive
aws/platform/ Everything else: the entry point, the servers, the software, the sign-in service. The first step of removal. Disposable, changes on release
shared/realm/ Sets up the identity service: the sealed set of users, the two registered programs, the roles, the first administrator. No Amazon names in here, ever. Shared configuration
shared/app-settings/ Builds the list of settings handed to the software when it starts. No Amazon names in here, ever. Shared configuration
tenants/ The only client-specific files. Settings only — no instructions, and never a secret. Client settings
scripts/ The things Terraform does not do: the daily build and teardown, the removal proof report, the secret hand-back. Automation scripts
💡
Why three folders and not two? A database needs a network to sit in, and the platform needs to know where the database is. With two folders that is a circle. Three breaks it, and the split matches how long each part actually lives: the network is cheap to keep, the data must survive, the platform is replaced constantly.

shared/ holds the two parts that would be identical on any cloud. With one cloud it is a module used once, which is a little indirection for no immediate gain. It is kept because it enforces the rule above — if an Amazon name ever appears in either, something has gone wrong.

Running It

Two commands, the same two for every client and every environment.

make bootstrap TENANT=acme ENV=production   # once — creates the record store
make apply     TENANT=acme ENV=production   # network, then data, then platform
ℹ️
Expect the first run to stop. The network layer waits for the client to point their web address at the new zone before the certificate can be issued. That is the internet's address system, not a fault. Give it the name servers the layer prints, wait for them to take effect, and run again.

Between the data layer and the platform layer the pipeline runs one more thing: a small task inside the network that creates the two databases, their users and the two extensions. Terraform cannot do it, because the database is private and Terraform runs from outside. See aws/data/db-setup.md.

Removal is two deliberate steps:

make remove-1 TENANT=acme ENV=production    # safe. Cannot reach the data.
make remove-2 TENANT=acme ENV=production    # destroys it. After the waiting period.
make proof    TENANT=acme                   # what is left, read from the account

Rules That Are Not Negotiable

  1. One client environment per run, one record per environment. Never a loop over clients. A mistake on one client must not be able to reach another.
  2. Nothing under aws/ or shared/ is ever edited for one client. If a client's request makes you want to, it belongs in their settings file, or it is a request to refuse.
  3. No secret in a settings file. Every password and key is generated during the install and written straight into the client's secret store.
  4. Data is retained, not destroyed. The everyday teardown cannot reach the database or the documents — that is why they live in aws/data/ with their own record.
  5. The run refuses to execute against any account other than the one in the settings file.
  6. Everything carries the four tags — client, environment, managed-by, release. The proof that a removal was complete is a tag query, and it only works if this holds.

The Daily Cycle, Once an Account Exists

make dev-up   TENANT=dev    # network, data, platform — 8 to 12 minutes
make dev-down TENANT=dev    # tears it all down again

An environment left running overnight and at weekends costs roughly three times what it costs during working hours, and nobody is using it. dev-down deletes the database — that is right for development and wrong everywhere else. It keeps the DNS zone and the certificate, because recreating the zone changes its name servers and would mean re-delegating the web address every morning.

🛑
Teardown Safety Guardrail: It refuses to run against any account except the one named in KAITO_DEV_ACCOUNT or tenants/<tenant>/dev-account. A teardown script that works anywhere is a loaded gun.

Start-to-End Creation & Execution Flow

How the environment is created sequentially from start to finish, which file runs first, what each step does, and what happens next:

Step 0 · Syntax & Contract Validation (Runs First - Offline)
Command: make validate • File: validate.ps1
Validates that all 11 Terraform slices parse correctly, providers resolve, and required settings files exist in tenants/<TENANT>/<ENV>.tfvars without needing an AWS account.
Step 1 · Remote State Bootstrap (Run Once Before Everything)
Command: make bootstrap TENANT=acme ENV=production • Folder: aws/bootstrap/
Creates the dedicated Amazon S3 bucket to hold Terraform's state records (`.tfstate`). Terraform cannot store its state file in S3 until this bucket exists.
Step 2 · Network Infrastructure Setup (Layer 1)
Command: make network TENANT=acme ENV=production • Folder: aws/network/
Provisions the private VPC, subnets, NAT Gateway, Route 53 DNS zone, and ACM SSL certificate.
⚠️ Pause Condition: The run waits here for the client to point their domain name servers to Route 53 so ACM can issue the SSL certificate.
Step 3 · Persistent Data Layer & DB Task (Layer 2)
Command: make data TENANT=acme ENV=production • Folder: aws/data/
Provisions the private PostgreSQL RDS database, S3 document storage, and KMS encryption keys.
Internal Task: Executes aws/data/db-setup.md inside the private VPC to create DB users, schemas, and extensions.
Step 4 · Application & Platform Layer (Layer 3)
Command: make platform TENANT=acme ENV=production (or make apply for full chain)
Folder: aws/platform/
Deploys ALB load balancers, Elastic Beanstalk/EC2 hosting, ECR registries, CloudFront CDN, Secrets Manager secrets, IAM roles, and CloudWatch logging. Connects application servers to network & database layers.
Step 5 · Controlled Teardown & Removal Proof
Safe Teardown: make remove-1 (Tears down disposable platform servers, leaves DB intact)
Complete Removal: make remove-2 (Destroys database & network after client confirmation)
Proof Audit: make proof • Runs scripts/removal-proof.sh to verify zero resources remain tagged in AWS.

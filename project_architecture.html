Step-by-Step Execution Flow
validatebootstrapnetworkdataplatform
0

make validate — Syntax Check (No AWS Account Needed)

Validates all 11 Terraform slices parse correctly, providers resolve, and settings contract is met. Runs entirely offline — no AWS credentials required. Run this first to catch errors before spending money.

B

make bootstrap TENANT=acme ENV=production — Run Once

Creates the S3 state bucket kishor-tfstate-acme-{account_id} in ap-south-1. Run exactly once per client. If the bucket already exists, skip this step. Without it, all other layers will fail with "NoSuchBucket".

1

make network TENANT=acme ENV=production — Layer 1

Provisions VPC, subnets, NAT, Internet Gateway, Route Tables, Security Groups, Route 53 DNS zone, and ACM SSL certificate. Expect a pause after this — the client must delegate their domain to Route 53 nameservers before the SSL cert can be verified. State saved to production/network.tfstate.

2

make data TENANT=acme ENV=production — Layer 2

Reads Layer 1 state from S3, then provisions RDS PostgreSQL (Multi-AZ, 200 GB), S3 document bucket, and KMS encryption key. After this: run the manual DB setup task inside the VPC to create schemas and users (see aws/data/db-setup.md). State saved to production/data.tfstate.

3

make platform TENANT=acme ENV=production — Layer 3

Reads both Layer 1 and Layer 2 state from S3. Deploys ALB, EC2/Beanstalk (2× t3.medium backend + 2× t3.small auth), CloudFront CDN, ECR, IAM roles, Secrets Manager secrets, CloudWatch logs and alarms, schema migration job. Platform is designed to be replaced on every software release. State saved to production/platform.tfstate.

🚀
TIP: Run all 3 layers at once with a single command:
make apply TENANT=acme ENV=production

Terraform State Dependency Chain
💡
What is state? Terraform keeps a record ("state") of every AWS resource it created. This record is stored as a JSON file in S3. When a later layer needs to know something (like the VPC ID), it reads the earlier layer's state file from S3. This is called remote state.

📦 S3 Bucket: kishor-tfstate-acme-482094833964

All 3 state files live here, in the same bucket, different keys
📄 production/network.tfstate (written by Layer 1)
vpc_id public_subnet_ids private_subnet_ids security_group_alb security_group_app security_group_auth security_group_db zone_id certificate_arn name_servers
📖 Layer 2 (data) READS: private_subnet_ids, security_group_db → to know where to place the RDS database
📄 production/data.tfstate (written by Layer 2)
db_address db_port db_name db_master_secret_arn documents_bucket documents_bucket_arn kms_key_arn
📖 Layer 3 (platform) READS both state files → network for VPC/subnets/certs, data for DB address/bucket/KMS
📄 production/platform.tfstate (written by Layer 3)
app_url api_url auth_url organization_id hosting_summary schema_version removal_tag
How Platform Reads Remote State (in aws/platform/main.tf)
# Layer 1 state is read like this:
data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket = var.state_bucket # "kishor-tfstate-acme-..."
    key = "production/network.tfstate"
    region = var.aws_region
  }
}

# Layer 2 state is read like this:
data "terraform_remote_state" "data" {
  backend = "s3"
  config = { key = "production/data.tfstate", ... }
}

# Values are then aliased into locals so the rest of platform never
# reaches into remote_state directly:
locals {
  vpc_id = data.terraform_remote_state.network.outputs.vpc_id
  db_address = data.terraform_remote_state.data.outputs.db_address
  cert_arn = data.terraform_remote_state.network.outputs.certificate_arn
}

Security Design
1

🚫 No Secrets in Files — Ever

Every password and key is generated during the install and written directly to AWS Secrets Manager. Nothing sensitive appears in any .tf, .tfvars, or .hcl file. Secrets are never logged, never in Git, never in Terraform state in plaintext.

2

🔐 Account Guard — Wrong Account = Blocked

Every Terraform provider block includes allowed_account_ids = [var.aws_account_id]. If the TENANT argument points to the wrong account, Terraform refuses to run. A typo on the command line cannot accidentally destroy production.

3

🏷️ Four Mandatory Tags on Every Resource

Every single AWS resource carries kaito:tenant, kaito:environment, kaito:managed-by, and kaito:release. This enables tag-based removal proof: a tag query returning zero resources proves the environment is completely gone.

4

🗄️ Data Is Retained, Not Destroyed

The everyday teardown (make remove-1) cannot reach the database or documents — they live in the data layer with their own Terraform state file. The platform layer has no resource block for the database, so it is structurally impossible to destroy it from a platform destroy.

5

🔒 Database Is Completely Private

RDS is placed in private subnets with publicly_accessible = false. The DB security group only accepts connections from the App and Auth security groups. No SSH. No direct internet access. No public IP. Terraform itself runs from outside the VPC so it cannot reach the DB — which is why the manual db-setup.md task exists.

6

✏️ One Client Per Run — No Loops

You always specify exactly one tenant and one environment. The Makefile and Terraform code never loop over multiple clients. A bug or mistake in one run is physically contained to one client's AWS account.

# Checklist before running remove-2:
1. Take a full database export and hand it to the client
2. Wait the agreed holding period (default: 30 days)
3. Set db_deletion_protection = false in production.tfvars
4. Run make remove-2 and type the client name when prompted
5. Run make proof — verify the output is empty
6. Send the proof output to the client as confirmation
